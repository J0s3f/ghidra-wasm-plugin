# REPORT-H - real-world WebAssembly corpus sweep

Status: **complete**. Plugin under test: this worktree (`feat/wasm-corpus`, base `1e2328b`), built
against Ghidra 12.1.4. Expectations reference `MODERN_WASM_GAPS.md`. No plugin source was modified.

Machine artifact: `test-scripts/corpus-RESULTS.md` (regenerated by the sweep, per-module logs
alongside it). Harness: `test-scripts/corpus-sweep.ps1`, `test-scripts/corpus/`, probes in
`test-scripts/probes_corpus.py`.

## Headline numbers

* **15/15 modules imported.** No import failures, no loader errors (`No load spec found` and friends
  never appeared).
* **5591/5591 functions decompiled** (0 decompile failures) - 1,465,308 instructions total.
* **Real decode gap: 933 - 932 = 1 byte, in one module, and that module is invalid input.** Every
  module that V8 accepts has `undefined_bytes == 4 x (number of imported functions)`; subtracting
  those placeholders leaves **0 undefined bytes for all 14 valid modules**.
* **0 unimplemented instructions**, and function accounting is exact: for all 15 modules
  `Ghidra functions == wasm defined functions + imported functions`.
* 2 analysis `ERROR` lines total: one on the invalid module (correct rejection), one from a *core*
  Ghidra analyzer (`PngDataType`) unrelated to wasm.
* 255 analysis `WARN` lines: 233 are the decompiler being handed the imported-function placeholders
  (F1) and **22 are `WasmStackVariableAnalyzer` "Variable storage conflict" failures on valid
  modules** (F2).
* The corpus does **not** exercise any item on the unsupported-feature list: mainstream
  wasm-bindgen / Emscripten output is MVP + 2.0 (+ SIMD/atomics/ref-types/multivalue). See §4.

## 3. Ranked findings (worst first)

### F1 - imported functions become empty 4-byte bodies in an `EXTERNAL` block (medium; measurement + minor defect)

Every imported function is modelled as a 4-byte, zero-instruction body in a dedicated `EXTERNAL`
memory block. `undefined_bytes` therefore equals `4 x imports`, and the decompiler logs a pcode
error for each.

Evidence:

* Invariant across the corpus - `undef == 4 x imports` without exception:
  `rasterbator 156=4x39`, `oxipng 4=4x1`, `oxipng_parallel 56=4x14`, `jpeg_dec 104=4x26`,
  `jpeg_enc 112=4x28`, `webp_dec 72=4x18`, `webp_enc_simd 92=4x23`, `avif 124=4x31`,
  `sqljs 152=4x38`, `tree_sitter 36=4x9`, and `0` for the four modules with no imports.
* The `EXTERNAL` block is exactly `4 x imports` bytes: `rasterbator EXTERNAL=156`, `sqljs=152`,
  `tree_sitter=36`.
* `CorpusProbe.java`, rasterbator: all 39 undefined functions are
  `body=4 instrs=0 undef_bytes=4`, at `ram:7f000000 + 4*i`, first one
  `__wbg_new_with_u8_clamped_array_and_sh_... @ ram:7f000000`, each followed by
  `PREVIEW (no instructions)`. Total `empty_bodies=39` == `imports=39`.
* Decompiler: 233 WARN lines, exactly one per imported function, of the form
  `Decompiling ram:7f0000xx, pcode error at ram:7f0000xx: Unable to disassemble EXTERNAL block location: ram:7f0000xx (DecompileCallback)`
  (e.g. rasterbator 42, sqljs 38, avif 31).

Why it matters:

* `undefined_bytes` is documented as *the* key metric ("a healthy module has 0"). With the corpus, a
  perfectly-decoded 1.1 MB module reports `124`, and the biggest module reports `152`. Any CI gate on
  this metric would be measuring the import count, not decode quality. The sweep therefore reports
  `undef*` as well (see §2); `CorpusProbe.java` emits `thunk_bytes` for it.
* The imported functions cannot be inspected or decompiled; each call site triggers a pcode error.

Not a regression: `MODERN_WASM_GAPS.md §2.4` records `437/437` decompiled for the Rasterbator module
(we reproduce `437/437`), but never published its `undefined_bytes`, so there is no baseline to
compare against. Classification: **correct-ish modelling with a misleading metric and noisy
decompilation** - worth a decision (either exclude import placeholders from the metric, or give the
imports real thunk bodies).

### F2 - `WasmStackVariableAnalyzer` gives up on 22 instructions where stack slots overlap at different widths (medium; real analyzer gap on *valid* modules)

On four valid corpus modules the stack-variable analyzer logs a warning and **skips** the instruction
instead of recovering the access:

```
WARN Failed to process instruction at ram:80010392: i32.store align=0x2 offset=0x390:
     Variable storage conflict between local_240{Stack[-0x240]:4} and local_23e{Stack[-0x23e]:2}
```

Distribution (22 total): `jsquash_png_codec` 14, `jsquash_oxipng_parallel` 3, `rasterbator_rs_bg` 3,
`jsquash_oxipng_codec` 2.

The conflicting pairs always overlap *partially* and differ in size, e.g.

* `local_2{Stack[-0x2]:2}` vs `local_1{Stack[-0x1]:1}` - `i32.load16_u align=0x1 offset=0x0`
  (`ram:80014e33`, `ram:8001504f`, `ram:8000a23d`, `ram:8001c9ff`)
* `local_b4{Stack[-0xb4]:4}` vs `local_b3{Stack[-0xb3]:1}` - `i32.store align=0x2 offset=0x1c`
  (`ram:80008d93`, `ram:80008ffe`, `ram:800090d5`, ...)
* `local_240{Stack[-0x240]:8}` vs `local_23c{Stack[-0x23c]:4}, local_23e{Stack[-0x23e]:2}` -
  `i64.load align=0x2 offset=0x390` (`ram:800104c0`)
* `local_28{Stack[-0x28]:8}` vs `local_24{Stack[-0x24]:4}` - `i64.load/i64.store align=0x3 offset=0x0`
  (`ram:8000e07c`, `ram:8000e135`)
* `local_382c{Stack[-0x382c]:8}` vs `local_3828{Stack[-0x3828]:4}` -
  `i64.store align=0x2 offset=0x34` (`ram:800011e2`)

This is the pattern Rust/LLVM and C compilers produce whenever one memory region is reused at
different widths (union/`memcpy`-style punning, slot reuse, `i8`/`i16`/`i32` aliasing). Ghidra cannot
represent two overlapping stack variables of different sizes at the same offset, and the analyzer
elects to bail out per instruction rather than to fall back to the widest (or a synthetic) variable.
The instructions still disassemble and the functions still decompile, so the cost is missing stack
variables / raw pointer arithmetic in those spots, not a crash. Classification: **real analyzer gap**;
candidates are "use the widest existing slot" or "emit a byte-array/synthetic variable" rather than
warning + skip.

### F3 - a malformed function body is rejected, but a bogus `unreachable` is left where the locals header is (medium; robustness, roadmap item 0)

`minrepro_a_i32` is `(func (param i32 i32) (result i32))` with body bytes `00 0b` (0 locals, then
`end`) - the body is empty but the signature promises an i32, so the module is invalid. V8 agrees:
`INVALID ... expected 1 elements on the stack for fallthru, found 0 @+33`. Ghidra:

```
ERROR Failed to analyze function f @ ram:80000020 (WasmPreAnalyzer)
      wasm.analysis.ValidationException: Validation error at address ram:80000021: pop from empty stack
UNDEF func=f entry=ram:80000020 body=2 instrs=1 undef_bytes=1 ranges=ram:80000021+1
PREVIEW ram:80000020  unreachable
```

The pre-analyzer correctly rejects the body, but the function is still created over the 2-byte body
range starting at the *locals-count byte* (`0x00` at `ram:80000020`), which the fallback disassembler
decodes as `unreachable` (opcode `0x00`); the real `end` (`0x0b`) at `ram:80000021` is left
undefined. So a malformed body does not degrade to "nothing here" - it degrades to a *wrong* listing.

Containment is good though: in the reduced probe `C02_invalid_body.wasm` the second (valid) function
in the same module still analyses and decompiles (`funcs=2 undef=1 decomp=2/0`), i.e. the failure is
per-function, not per-module. Classification: **real robustness bug** - the same root cause as
roadmap item 0 ("graceful degradation for unknown opcodes"); an unknown/invalid body should produce
zero instructions or an explicit "unsupported" pseudo-instruction, never a misaligned `unreachable`.

### F4 - core Ghidra `PngDataType` analyzer errors on wasm memory (low; not this plugin, but it pollutes metrics)

`jsquash_png_codec` is the only valid module with an `ERROR` line:

```
ERROR Invalid PNG data at ram:0010e274 (PngDataType)
```

This is a stock Ghidra analyzer scanning the wasm `.memory0` block (1 MiB of analysable data) and
believing it found a PNG. It is not a defect in the WebAssembly plugin, but it means an
"error-count == 0" CI gate over real-world modules will produce false failures, and the analyzer
wastes time on every wasm memory block. Classification: **environment/noise, not a wasm-plugin bug**.

### Not a finding: `global.get`/`global.set` operands

Listings show `global.get 0x00000000`, `global.get 0x00000010`, ... `global.set 0x000000d0` in
`web_tree_sitter` (which has 15 globals: 6 imported + 9 defined). These are multiples of 0x10, i.e.
the *address of the global's 16-byte slot*, not the global index - consistent with one 16-byte slot
per global (a `v128` global fits). No out-of-range index is implied. Listed only because a reader
comparing against the index could mistake it for a bug.

## 4. Expected-unsupported vs real bug

The corpus contains **no** module that exercises an item on the `MODERN_WASM_GAPS.md` unsupported
list. All 15 are MVP + WebAssembly 2.0, plus SIMD128 / atomics / reference-types / multivalue /
bulk-memory, i.e. exactly what current wasm-bindgen and Emscripten emit. Consequences:

* Everything the corpus hits is in the "works" column - so the three real findings above (F1, F2, F3)
  are the *only* defects this sweep can attribute, and none of them is on the unsupported-feature
  list.
* The documented gaps (multi-memory, memory64, stack switching / JSPI, JS string builtins, wide
  arithmetic, custom page sizes, component model, GC, new EH, typed function refs) are **not
  reachable from this corpus** and remain covered by the synthetic probes in `probes_*.py` /
  `gen_feature_probes.py` only. A corpus sweep cannot replace them - deliberately constructing such
  modules requires a toolchain (Kotlin/Wasm, Dart, LLVM 19+, `wasm-tools`) that is not part of this
  environment.
* `minrepro_a_i32` fails, but V8 also rejects it, so it is **malformed input**, not a
  missing-feature failure. It is kept as a negative control.

Doc discrepancy worth a follow-up: `MODERN_WASM_GAPS.md §9` says `.debug_line` import is disabled to
avoid an `AddressOutOfBounds` failure, but `rust_debuginfo` (which has `.debug_line`,
`-C debuginfo=2`) imports cleanly and exposes a `.debug_line` memory block of 21711 bytes with no
error. Either the doc is stale or the block is created without actually applying line info. This is
**not** a failure, but it contradicts the doc and deserves a check (open question Q2).

## 6. Open questions

1. **Should imported functions have bodies at all?** F1 suggests the 4-byte placeholders are dead
   weight that corrupts the headline metric. Is the intent a thunk (a `call`/`unimplemented` at the
   import address) or no body? A decision here also settles whether `WasmFeatureReport`'s
   `undefined_bytes` should exclude them.
2. **Is `.debug_line` import actually enabled?** `rust_debuginfo` gets a `.debug_line` block and no
   `AddressOutOfBounds` error, contradicting `MODERN_WASM_GAPS.md §9`. Was it re-enabled in a merged
   branch, and is line info actually applied to addresses? (Check for source-line comments in a
   listing of `rust_debuginfo`.)
3. **Is the `unreachable`-at-the-locals-header behaviour specific to a failed pre-analysis, or does
   it also appear for other aborts** (e.g. a body that trips a validation error mid-way, like the
   `memory64` case in `MODERN_WASM_GAPS.md §2.2`)? Probe `05_memory64` (1 instr, 6 undefined bytes)
   looks like the same signature - worth confirming they share a root cause.
4. **`PngDataType` on `.memory0`** - is the wasm memory block supposed to be excluded from generic
   data analyzers? That is a loader (not loader-logic) question, but it affects every wasm import.
5. **Rust name demangling** - `rust_plain`/`rust_debuginfo` names come through as raw legacy
   `_RNv...` symbols (72 of them) while `fib`/`fmt` are readable. Not a bug, but a large usability
   gap for the Rust-heavy half of the corpus; is a demangler meant to be wired in (analogous to the
   GnuDemangler feature)?
6. **Corpus growth**: to make a future sweep able to attribute *unsupported-feature* failures, the
   corpus needs at least one module per gap (GC, typed refs, new EH, memory64, multi-memory, JSPI,
   string builtins, component model). That requires adding toolchains to the environment, or
   hand-assembling modules (which then overlap with the existing probes).
7. **What exactly triggers F2?** The conflicting slot pairs always mix two widths over an overlapping
   range, but which construct (union punning, `memcpy` into a slot, `i8`/`i16` aliasing, slot reuse
   across `if`/`loop`) is the minimal trigger is unproven. A minimal probe would make the
   "use the widest slot / synthetic variable" fix testable. Candidates to try first: an `i32.store`
   followed by an `i32.load16_u` at `base+1` on the same base, and a union-style pun with `i64`.
