## 1. What was actually wrong (beyond `DIAGNOSIS.md`)

`DIAGNOSIS.md` identified two defects. There was a third, upstream of both: **the previous fixture
was not a component-model binary at all.** `probes_component.py` inserted a fabricated 36-byte
"fixed header" (`flags` + nine 4-byte section indices) between the preamble and the first section.
The component-model binary format has no such field: the 8-byte preamble is followed immediately by
`section*` (WebAssembly/component-model `Binary.md`: `component ::= <preamble> s*:<section>*`,
`preamble ::= <magic> <version> <layer>`). Consequences in the old run:

1. The bytes `01 00 00 00` (the bogus "type section index = 1" field) were decoded as
   `id=1, size=0` - a **phantom core-module section**. That, not re-scanning, is where
   "total modules found so far: 2" came from.
2. The old code then *did* re-point the reader into the payload and never restored a clean
   end-of-section position, so a real nested module's own `type` section (id `1`) was also a
   phantom-module hazard once the framing was fixed.

The old loader's `load()` only logged and created no memory blocks, which is why the import died with
`No memory blocks were defined` inside the core-module path. Detection (magic + `version != 1`) was
the only sound part and is kept.

## 2. What I changed in the scaffold

`WasmComponentLoader.java` was rewritten (same class, same loader name/registration):

* **Real header handling.** The 8-byte preamble is split into `magic(4) + version:u16 LE + layer:u16 LE`
  instead of `magic(4) + u32 version`. A file is a component candidate iff it has the magic and its
  4 bytes at offset 4 are not the core module's `01 00 00 00` (i.e. not version 1).
* **Correct section framing with size-based skipping.** Sections are read as `id:u8`,
  `size:u32 LEB128` (hand-rolled LEB reader with explicit truncation/over-long checks), then the
  reader jumps to `payloadStart + size`. A payload is **never** walked, so a nested module's own
  section ids (its `type` section is id `1` too) cannot produce a phantom core module.
* **Core-module recognition, not id-only.** A section `id 1` counts as a core module only if its
  payload has the core preamble `\0asm` + `version == 1` (`isCoreModule`). Anything else logged and
  skipped instead of being counted.
* **Real loading.** `load()` wraps the module's sub-range in a `ByteProviderWrapper` and delegates to
  `new WasmLoader().load(program, moduleSettings)` (see §4).
* **Exactly one `LoadSpec`.** The loader always loads the first module, so it offers a single import
  entry regardless of how many modules exist (offering one per module produced duplicate,
  indistinguishable options).
* **Clear logging:** version/layer, `found N core module section(s)`, and
  `loading core module index I of N (component section S, file offset 0x..., size ... bytes) through WasmLoader`.
* **Graceful degradation:** short/absent/over-long sizes log `truncated component: ...` and stop;
  zero modules logs `component header detected but no core module sections (section id 1) found in
  the binary; no load spec offered.` and returns no `LoadSpec` (import fails with `No load spec found`).

`probes_component.py` was rewritten to emit **spec-valid** components (preamble + real sections) and
to print a byte-offset map. It still honours `sys.argv[1]` as the output directory and generates the
three fixture names the acceptance run imports.

## 3. The component section layout that is parsed (fixture offsets)

`component_with_module.wasm` = 62 bytes, generated by

```powershell
python test-scripts\probes_component.py <outdir>
# 0x0000  preamble (\0asm, version 0x000d, layer 0x0001)
# 0x0008  section id 1 (core:module), size=35 (0x23)
# 0x000a  nested core module payload (35 bytes, \0asm + version 1)
# 0x0012    (inside payload) nested core type section id 1 - must NOT be re-scanned
# 0x002d  section id 0 (component custom section "probe")
```

Byte-level map (verified by hexdump):

| offset | bytes | meaning |
| --- | --- | --- |
| `0x00` | `00 61 73 6d` | magic `\0asm` |
| `0x04` | `0d 00` | version `0x000d` |
| `0x06` | `01 00` | layer `0x0001` |
| `0x08` | `01` | component section id `1` = `core:module` |
| `0x09` | `23` | payload size, u32 LEB128 = 35 |
| `0x0a` | `00 61 73 6d 01 00 00 00` | payload = complete core module: magic + version 1 |
| `0x12` | `01 06 01 60 01 7f 01 7f` | (nested) core **type** section, id `1` - the phantom-module trap |
| `0x1a` | `03 02 01 00` | (nested) function section |
| `0x1e` | `07 05 01 01 66 00 00` | (nested) export section: `"f"`, func, idx 0 |
| `0x25` | `0a 06 01 04 00 20 00 0b` | (nested) code section: 1 body, `local.get 0`, `end` |
| `0x2d` | `00 0f 05 "probe" 63 6f 6d 70 6f 6e 65 6e 74` | component custom section id `0` (skipped by size) |

The nested module is byte-identical to `gen_feature_probes.py` probe 01 (`01_baseline_i32.wasm`),
which is why the metrics equal probe 01's.

Other fixtures:

* `truncated_component.wasm` - 26 bytes: preamble + `01 40` (section id 1 declaring 0x40 payload

## 4. How the extracted module becomes a real program

`WasmComponentLoader` is in package `wasm`, the same package as `WasmLoader`, and `WasmLoader`'s
entry point `protected void load(Program, ImporterSettings)` is therefore reachable without any edit
to `WasmLoader.java`:

```java
ByteProvider moduleProvider = new ByteProviderWrapper(provider, module.offset, module.size);
ImporterSettings moduleSettings = new ImporterSettings(moduleProvider, settings.importName(),
    settings.project(), settings.projectRootPath(), settings.mirrorFsLayout(), settings.loadSpec(),
    settings.options(), settings.consumer(), settings.log(), settings.monitor());
new WasmLoader().load(program, moduleSettings);
```

* `ByteProviderWrapper(ByteProvider, offset, length)` maps the sub-range onto index 0 (`length()`
  returns the sub-length, `readBytes` adds the offset, `close()` is a no-op), so `WasmLoader` reads a
  self-contained core module.
* `ImporterSettings` is a public record in Ghidra 12.1.4 (`ghidra.app.util.opinion.Loader$ImporterSettings`)
  with a public canonical constructor, so it can be re-created with the wrapped provider.
* `WasmLoader.doLoad` then creates the `.module` block from the 35 module bytes and runs its normal
  function/table/memory/global/data loading. `WasmAnalysis` (used by every analyzer) re-parses the
  module from the `.module` block at `ram:CODE_BASE` (`WasmLoader.getModuleAddress`), so auto-analysis
  sees the nested module - this is exactly why metrics match a standalone probe-01 import.
* Visibility note / requested hook: I rely on `WasmLoader.load(Program, ImporterSettings)` being
  package-visible. If that visibility is ever tightened, the exact hook needed is a public entry
  point such as `public void loadCoreModule(Program, ByteProvider moduleProvider, ImporterSettings)`.
  No change to `WasmLoader.java` was required today.

file whose version is 1, so `WasmLoader` keeps handling them alone.

## 7. Not supported / deliberately out of scope

* **Nested components** (section id `4`) and their core modules: payloads are skipped by size, so
  modules inside a nested component are not extracted. Logged as "no core module sections" if there
  is nothing else.
* **Component-level index spaces** (core instances id 2, core types id 3, instances id 5, aliases id 6,
  component types id 7, canon id 8, start id 9, imports id 10, exports id 11, values id 12) are not
  modeled; only `core:module` (id 1) is recognized.
* **Cross-module instantiation / the component's actual semantics** (canon lift/lower, type
  matching, resource types, start function): none of it is analyzed. The program is simply the first
  embedded core module - which is the documented pragmatic first step (roadmap item 10).
* **Module selection**: only module index 0 is loaded; there is no option/UI to pick another module
  of a multi-module component (the count is logged).
* Version 13 / layer 1 is the only component flavour produced by the probes; the detector accepts any
  non-version-1 magic file, but only `\0asm`+version-1 payloads are recognized as core modules.
