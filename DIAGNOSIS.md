# Diagnosis handed to the component-model workstream (integrator notes)

The previous attempt (model `free-nemotron-lightning`) produced the scaffold in this worktree
(`WasmComponentLoader.java`, `test-scripts/probes_component.py`, `REPORT-C.md`). Its report claims
success, but **independent verification fails**. Do not trust the report; use this document.

## What actually happens (reproduced by the integrator)

Fixtures are generated by `test-scripts/probes_component.py <outdir>`; the interesting one is
`component_with_module.wasm` (component header + one core-module section whose payload is the
`01_baseline_i32` module).

Importing it through `analyzeHeadless` produces:

```
WasmComponentLoader: Found core module index 0 embedded in component; total modules found so far: 1
WasmComponentLoader: Found core module index 1 embedded in component; total modules found so far: 2
WasmComponentLoader: Found 2 core module(s) from component; first module index loaded via LoadSpec
WasmComponentLoader: Core module section ID 1 found; extracting core module 1
WasmComponentLoader: Core module section ID 1 found; extracting core module 2
WasmComponentLoader: Loaded 2 core module(s) from component; first module index loaded
ProgramLoader: Using Loader: WebAssembly
...
Error: No memory blocks were defined for file .../component_with_module.wasm
Import failed for file: .../component_with_module.wasm
```

So: **the import still fails**, and it fails *inside* the core-module path (no memory blocks were
created, i.e. the program that was built does not contain a valid core module). Two concrete defects:

1. **Section framing is wrong.** A component with exactly *one* core-module section is reported as
   having **two**, and "extracting core module 1/2" runs twice. Component section framing is
   `id:u8` + `size:u32 LEB128` + payload; nested payloads must be skipped by their declared size, and
   a nested core module's payload must not be re-scanned for section ids (the nested module's own
   type section is id `0x01` too - that is almost certainly where the phantom second "core module"
   comes from). Also note the component header is 8 bytes (`\0asm` + version 2 bytes + layer 2 bytes),
   not magic + u32 version.
2. **The extracted module is not actually loaded as a program.** Whatever the loader produces ends up
   as a program with no memory blocks. The extracted core-module bytes must be handed to
   `WasmLoader` (the existing core-module loader) - e.g. by wrapping the extracted sub-range in a
   `ByteProvider` and delegating to `WasmLoader.load(...)`, or by writing the extracted module bytes
   to a temp file and importing that through the normal path - so that the resulting program has the
   module's memory/table/function blocks and analyzers run over it.

## Definite acceptance criteria (verified by the integrator)

1. `component_with_module.wasm` **imports**, and the resulting program is the nested core module:
   `WasmFeatureReport.java` must print `funcs=1 instrs=3 undefined_bytes=0 decompiled=1
   decompile_failed=0` (the baseline module's single function `f`), and `ListProgram.java` must show
   that function (`local.get l0` / `end`).
2. Exactly **one** core module is reported for that fixture (no phantom second module).
3. `bare_component_header.wasm` and `truncated_component.wasm` must **not** crash anything: the
   loader is allowed to report "no core module sections found" and let the import fail (that is the
   current behaviour, and it is acceptable).
4. Core modules are unaffected: the real-module regression must stay
   `SUMMARY functions=437 decompiled=437 failed=0 instructions=61658` and the frozen probe baseline
   (`MODERN_WASM_GAPS.md` §2.4/§2.5, probes 01-27) must keep its recorded metrics.
5. `MODERN_WASM_GAPS.md` §2.3 row "Component model binaries" may only be marked fixed once (1) holds;
   the integrator updates the doc, not you (do not edit it).

## Note appended by the component-model-2 workstream (`REPORT-C2.md`)

Additional root cause found: the previous `probes_component.py` fixture was not a valid component
binary - it inserted a fabricated 36-byte "fixed header" between the 8-byte preamble and the first
section. The component format has no such field, and the bytes `01 00 00 00` in that fake header
decoded as a phantom `id=1, size=0` core-module section. The fixture has been rewritten as a real
component (preamble + `id:u8 size:u32-LEB128 payload` sections) and the loader now skips every
payload by its declared size, extracts the first embedded core module into a `ByteProviderWrapper`
sub-range, and delegates to `WasmLoader.load(Program, ImporterSettings)` (same package `wasm`, so no
edit to `WasmLoader.java` was needed). All four acceptance criteria verified; a control run with the
loader removed from the jar produced byte-identical probe 01-27 metrics.
